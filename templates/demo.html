4가지 업무 체험

변경을 검수하고, 테스트를 보완하고, 배포 누락을 찾고, 로그를 연결합니다. 입력을 바꾸며 제가 만든 시스템의 판단 기준을 살펴보세요.

가상 데이터로 만든 설명용 데모 · 실제 회사 시스템의 복제가 아닙니다. 실제 AI·MCP·DB·Jira에 연결하지 않습니다. 결과는 미리 정한 예시이며, 상태는 이 페이지 안에서만 유지됩니다.

DBQ · 코드 해석과 판정의 책임을 나누다

AI가 SQL·업무 맥락을 정리하고, 원격 결정적 코어가 게시 SSOT로 판정합니다. 답변은 최신 재검수에서 해소 여부를 확인합니다.

실제 구조에서 데모가 보여주는 범위
  • 로컬은 사용자가 명시적으로 요청합니다. 코드를 편집하거나 커밋했다는 이유만으로 검수를 시작하지 않습니다.
  • AI의 SQL 도출 결과와 Remote MCP 코어 판정은 다릅니다. 불확실한 SQL은 소스 보완이 필요합니다.
  • 개발자 질문과 DBA의 승인 전·실행 전 확인을 구분합니다. ‘승인합니다’라는 말로 업무 근거를 대신하지 않습니다.
  • DDL은 코딩 가이드, DML은 최신 검수의 티켓 미리보기와 생성 동의로 이어집니다. PR 검수는 별도 실행이며 이전 로컬 PASS를 복사하지 않습니다.

검사에 통과하면 개발 티켓의 통제 정보를 모아 배포 변경 요청을 생성·연결합니다.
DCR 생성 전

        
04 · Slack 승인 요청과 처리
승인 요청을 Slack으로 전달하고 승인자의 선택에 따라 Jira 상태 전환을 처리합니다.
승인 요청 전
Slack 요청 전달·상태 전환은 자동화되며, 승인 결정은 승인자가 합니다.

        
05 · 배포 시 승인 확인
배포 범위의 PR에 연결된 DCR 승인을 확인하고 미승인 또는 변경된 요청은 차단하는 예시입니다.
확인 전
이 체험은 가상이며 실제 GitHub·Jira·Slack이나 배포 시스템에 연결하지 않습니다.

        
개발 티켓을 선택하고 가상 PR을 생성하세요.

      

    

    

      
로그 · 제각각인 기록을 공통 언어로
서로 다른 서비스 로그를 공통 필드로 정리하고, 같은 기준으로 요청 흐름을 살펴보세요.
업무 배경 ↑

      

        

        
01 · 서비스마다 다른 기록
같은 요청도 서비스별 필드 이름과 메시지 형식이 달라 일관된 검색이 어렵습니다.
가상 서비스 로그
예시에서는 요청 식별자가 각각 traceId, trace, trace_id로 기록됩니다.

        
02 · 공통 규격 적용
필드 이름과 구조를 공통 규격으로 맞추는 예시입니다. 개별 서비스의 메시지는 유지합니다.
요청 식별자traceId / trace / trace_id → trace.id
서비스app / service / svc → service.name
심각도level / severity / lvl → log.level
공통 필드와 예외 응답 형식을 서비스에 전파하는 구조를 가상 데이터로 보여줍니다.

        
03 · 같은 기준으로 검색과 추적
이벤트 3건
표준화 후 확인할 수 있는 효과
같은 필드로 서비스 로그를 묶고, 하나의 요청을 따라가며 오류 지점을 찾을 수 있습니다. 예시는 가상이며 실제 장애 조회나 측정된 성과 수치는 아닙니다.

        
서비스별 기록을 확인하고 공통 규격을 적용해 보세요.
